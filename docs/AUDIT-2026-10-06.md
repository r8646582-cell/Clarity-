# Purpose: second audit, including prompts

Base: merged PR #6, commit 189ddb60468485684c0ab5e665427879020e6390.

This is a source and regression-test audit. CI verifies the unit suite and release compilation. It does not prove Redmi/HyperOS behavior, notification delivery, provider reply quality, or that the app has no remaining bugs. The previous promise/time/tree fixes remain in the base.

## Confirmed defects fixed in this pass

| Problem | Result after the fix |
| --- | --- |
| Tool reschedule example says `today` but its reason says tomorrow | Both fields say tomorrow. |
| Tool guidance promises a most-recent match while execution rejects ambiguous matches | Instructions now require a unique match and clarification. |
| Persona/modes teach legacy promise markers while the runtime teaches JSON actions | Runtime contract selects JSON for new promise changes and forbids emitting both formats for one change. Legacy parsing remains compatible. |
| Reflection rejects a full due timestamp, making a timed commitment undated | New and renegotiated commitments retain their clock. Date-only inputs remain supported. |
| Reflection has no per-message date in continued transcripts | Every reflection message now includes its full local timestamp. Supplemental instructions anchor relative dates to that message. |
| Legacy relative dates use yesterday before 4am, contradicting calendar today/tomorrow | Reply parsing uses the current calendar date. The conversational greeting still understands late nights. |
| Prompts allow leaving an exercise but the parser has no normal-mode transition | Explicit `[[mode: normal]]` clears the exercise; unknown mode names still fail. |
| Legacy datetime parsing silently cuts off a timezone suffix or trailing junk | Invalid local datetimes are rejected rather than changed. |
| Action receipts are globally consumed, so a different thread can see private results and a failed network attempt loses feedback | Receipts are scoped to the originating conversation and survive request preparation/retry. Storage holds only the latest receipt. |
| Test bench omits real chat's tool schema and hides canonical tool blocks | Scenarios receive the same action contract; reports show emitted blocks. No actions execute in the bench. |
| API cancellation hooks wait for the blocked operation to finish | A cancellation watcher closes the socket during both execute and response reads, for both providers. Cancellation stays cancellation rather than triggering network fallback. |
| Non-streaming completion parsers accept output cut off at the token limit | Both providers reject truncated output, preventing partial letters/snapshots from being stored as finished. |
| Journeys advance after two messages while the step conversation is still in progress | Automatic advancement occurs on session end; an explicit completion action can still advance immediately. |
| Remembered swipe callbacks retain the pre-edit item, so Undo can restore old wording or dates | Swipe callbacks read the current promise/memory item; overdue promise labels also retain the due clock. |
| Typed key and backup passphrase enter saved UI-state bundles | Secrets stay in transient component state; re-entry is required after recreation. Existing encrypted key storage is unchanged. |
| Backup/export/import actions can overlap and swallow cancellation as a failure message | One backup operation runs at a time; lifecycle cancellation propagates. |

## Prompt review

All 18 bundled prompt files were inspected, alongside their runtime fill sites and parsers. The supplied Markdown assets are not rewritten in this PR. CLAUDE.md reserves them for Umair and asks for proposed changes before edits; this pass changes the app's technical contract and records content proposals below.

| Files | Assessment / proposed polish |
| --- | --- |
| `persona.md`, `examples.md` | Strong voice, correction, privacy and uncertainty rules. Examples still model unsupported claims such as a third repeated failure and confident family interpretations. Change these to conditional observations unless evidence exists. Avoid carrying fictional calendar dates into real actions. |
| `reflection.md` | Durable memory, deletion and confidence rules are appropriate. Its date-only JSON example conflicts with retaining agreed times; runtime now supports timestamps. Consider documenting `YYYY-MM-DDTHH:mm` directly. Confirmed and user-edited entries remain protected by code even when generic correction wording asks the model to rewrite them. |
| `mode_decision.md`, `mode_practice.md`, `mode_journey.md` | Useful structure, but endings teach legacy promise syntax. Consider using the runtime action contract consistently and saving only an action the user actually agreed to. Journey day one should not ask how yesterday's action went unless one exists. |
| `mode_untangle.md` | Clear no-action boundary. The instruction refusing a requested decision can conflict with the persona's instruction to let him leave a mode. Clarify that an explicit request to switch/exit is honored, while ordinary pressure inside the exercise stays within it. |
| `mode_onboarding.md` | Explicit checklists and completion markers are good. The fixed hometown should be confirmed through his answers, and a skipped values exercise should not force invented values. Long conversations may need a compact checklist-progress block beyond the 16-message window. |
| `letter_weekly.md`, `letter_monthly.md` | Evidence-only and exact quote rules are good. Present next-period experiments as suggestions rather than already agreed commitments. Current profile/area state should not be used as proof of how a historical period started. |
| `gardening.md` | User edits are protected by execution. Prompt should also explicitly protect confirmed entries and deleted tombstones, and distinguish people with the same relation. |
| `snapshot.md` | Appropriate non-diagnostic framing. Recommending journeys from a static list can become stale after prompt edits/custom journeys; prefer the actual catalog supplied at runtime. |
| `milestone.md` | Good evidence thresholds. Example dates are fictional and should never be evidence. Runtime validation is necessary; a confident JSON field alone is not proof. |
| `chapter.md` | Compact historical format is appropriate. Distinguish contemporaneous evidence from current notes to avoid rewriting the past. |
| `journey_custom.md`, `journey_adapt.md`, `journeys.md` | Parseable structure and reasonable limits. Preserve explicit user changes and clarify that exploration completion differs from completing an outside action. Built-in outlines parse in existing tests. |
| `testbench.md` | Time-awareness fixture is internally inconsistent: 6 October 2026 is Tuesday, not Monday. Sunday 4 October 00:40 to Monday 5 October 08:00 is 31h20m; to Tuesday 6 October 08:00 is 55h20m. Correct fixture and expectation together. The empty-memory dodge scenario should not require assuming a repeated Monday pattern. Add consent, edits after midnight, duplicate/ambiguous targets, failed actions, private reminder, and mode-exit scenarios. |

## Further improvements, in priority order

1. **Show the saved result under the same reply.** Display the actual promise title/date/time after execution. The model currently writes its text before tools run; an emitted tool block cannot prove success. Failure feedback helps, but a deterministic save receipt would close this gap without a second AI call.
2. **Exercise destructive data replacement with active writers.** Restore/erase can reuse IDs while a background AI call is in flight. Session existence guards help ordinary deletion; a shared generation token or coordinated writer cancellation is a stronger protection. Add integration tests before changing this across all writers.
3. **Keep fresh mutable state in the volatile tail.** Promise IDs are refreshed; active journey/current step and settings-derived help numbers can still be stale in a cached context. Refresh small authoritative blocks without giving up the persona cache.
4. **Validate prompt editor saves.** Detect missing/unknown template fields and broken journey/testbench structure, with a useful error before accepting the edit. User overrides currently permit an unresolved placeholder to reach the provider.
5. **Make date/time labels refresh on resume and midnight.** Some Compose state is recomputed only on database emissions. Verify Path's day availability and due labels after leaving the screen open overnight.
6. **Offer accessible tree navigation.** Keep the timeline, and add explicit zoom/reset controls and readable selection feedback. Verify 50/300 leaves, large font sizes, and touch selection on the phone.
7. **Use a repeatable phone smoke run.** Create/edit a promise at 02:30 Karachi; cross midnight; change its due clock with a reminder; test offline send/reconnect and stop; background/lock during a reply; restore a backup on a fresh install; delete/undo memory and verify search; finish onboarding; pause/resume journeys; run the prompt bench; check day/night and large text.

## Trust and polish follow-up

The follow-up adds exact promise wording, absolute local date/time and reminder details under chat replies; typed repository results for edits, moves, resolutions and failures; and idempotent saving of an unchanged existing promise. Undo stays attached to creations, so editing an existing promise does not offer to delete it. Creation confirmations reflect the current stored promise. Edit/result receipts are transient, scoped to conversation and message, bounded to 100 replies and cleared on erase/restore/forget; in-flight receipt publication cannot repopulate a cleared store. Path remains the durable record after a process restart.

Memory edit sheets explain confidence and user correction protection and link to up to five surviving source conversations. Unknown provenance is stated explicitly. A model's confirmed observation is labelled strongly supported, rather than falsely saying the user confirmed it. Tree navigation gains visible Zoom out, Zoom in and Reset controls; Timeline remains the accessible list.

Long conversations receive a bounded bridge of four excerpts outside the 16-message window and the existing summary, after the cache prefix. It improves continuity without another API request; it does not recover every earlier turn. Prompt guidance discourages repeating answered questions, inventing history or motives, forcing commitments, or claiming a database save before execution. Voice examples remove unsupported repeated-history claims, inconsistent promise clocks, multiple questions and fixed calendar assumptions. The supplied persona is unchanged. Six new live test-bench scenarios cover these behaviors, and the Monday fixture is corrected to 5 October 2026.

Validation: new automated regressions cover confirmation timezone/date-only/failure behavior, context continuity and size, receipt isolation/retention/restore invalidation, and idempotent promise saves. Full Android unit tests and release compilation are verified through GitHub CI; local Gradle dependency download is unavailable in this workspace. Test-bench scenarios still require running with the user's configured provider and judging replies. No claim of a literal every-line proof, complete device testing or zero remaining bugs is made. Xiaomi reminder delivery, accessibility/font scaling, gesture selection and a real restore during active background work still need device verification. Clearing UI receipts is not a transaction barrier for all other in-flight writers.
